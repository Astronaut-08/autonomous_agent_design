# ReAct-агент для замовлення страв

## 1. Опис проєкту
Побудовано ReAct-агента на LangGraph для кафе. LLM: локальна модель Qwen3 через Ollama (`ChatOllama`, `temperature=0`, `reasoning=False`). Агент знаходить страви за запитом клієнта (категорія, дієта, алергени, ціна, час приготування), перевіряє їхню наявність, рахує вартість замовлення й орієнтовний час приготування.
Інструменти описані Pydantic v2 схемами з валідацією (`extra='forbid'`, `field_validator`). Виконання захищене запобіжниками (`max_steps`, `timeout`, `LoopDetector`), кожен крок пишеться в JSON-траєкторію, а фінальна відповідь повертається у структурованому форматі (`answer`, `confidence`, `sources`).

## 2. Доменна задача
- **Домен:** замовлення страв у кафе.
- **Що вирішує агент:** пошук і рекомендація страв за фільтрами (категорія, дієта, алергени, ціна, час), відповіді про склад і наявність, розрахунок вартості замовлення та часу приготування. Страви беруться з тестової бази `mock_data.json` (12 позицій).
- **Інструменти (tools):**
 - `search_items` — знайти страви в меню за ключовими словами, категорією, дієтою, алергенами, ціною та часом приготування. Недоступні страви, що підходять під запит, повертає окремим полем `unavailable_matches`.
 - `get_item_details` — отримати повну інформацію про одну страву за її id (формат `DISH-001`).
 - `check_availability` — перевірити, чи доступні зараз для замовлення вказані страви (1–10 id).
 - `calculate_order` — порахувати вартість замовлення за списком страв і кількостей, повертає суму та час приготування (максимум серед позицій).

## 3. Архітектура
- **LLM:** `qwen3` через Ollama. Модель з прив'язаними tools (`bind_tools`) приймає рішення в `agent`, окремі виклики з обмеженою довжиною генерації (`num_predict`) використовує `formatter`.
- **Граф:** `StateGraph(AgentState)` з трьома вузлами: `START → agent → (should_continue) → tools → agent → ... → formatter → END`. Стан містить `messages`, `step_count`, `final_response`, `stop_reason`, `formatter_fallback`. Якщо LLM повернула `tool_calls`, керування йде в `tools`, інакше у `formatter`.
- **Запобіжники** (у вузлі `agent`): `max_steps = 15`, `timeout = 120 с` (`time.monotonic()`, перевіряється перед кожним викликом LLM), `LoopDetector(max_repeats = 3)` (однаковий tool з однаковими аргументами 3 рази поспіль; аргументи хешуються як канонічний JSON з `sort_keys`). У разі спрацювання виклик не виконується, до історії додається службове повідомлення `[СТОП]`, і граф переходить до `formatter`, який повертає часткову відповідь із поясненням. Для LangGraph задано `recursion_limit = 2·max_steps + 5`.
- **Валідація:** усі схеми наслідують `StrictModel` (`extra='forbid'`). `handle_validation_error` повертає моделі текст помилки з назвами полів, тож модель може виправити виклик, а граф не падає.
- **Formatter:** текст `answer` береться з останнього повідомлення агента без змін (LLM його не переписує). Через `with_structured_output(AnswerMeta)` модель оцінює лише `confidence` і `sources`. Далі: `confidence` обрізається до [0, 1], `sources` фільтруються за id із результатів tools, а програмна гарантія дописує «Увага: зараз недоступно: ...», якщо в результатах tools була недоступна страва, а у відповіді про це не сказано. Після зупинки запобіжником formatter формує короткий підсумок із наявних результатів. Якщо структурований вивід не вдався, використовується запасне значення (`confidence = 0.3`, прапорець `formatter_fallback`).
- **Логування:** `TrajectoryLogger` пише кожен крок (`step_number`, `node_name`, `input`, `output`, `tool_calls`, `timestamp`, `duration_ms`) у JSON.

## 4. Інструкція запуску
1. Клонувати репозиторій: `git clone https://github.com/Astronaut-08/autonomous_agent_design.git`.
2. Перейти в директорію: `cd hw1_react_agent`.
3. Встановити залежності: `pip install -r requirements.txt`.
4. Встановити Ollama (API-ключ не потрібен, модель локальна):
 - Windows PowerShell: `irm https://ollama.com/install.ps1 | iex`
 - Linux / macOS: `curl -fsSL https://ollama.com/install.sh | sh`
5. Завантажити модель: `ollama pull qwen3` (сервіс Ollama має працювати, за потреби `ollama serve`).
6. Перевірити інструменти та запобіжники без LLM:
 - `python -m pytest -v` (63 unit-тести)
 - `python demo.py`
7. Запустити агента на тест-кейсах: `python test_runner.py` (створює `test_results.json` і `trajectory.json`).

- `formatter_fallback` не спрацьовував у жодному кейсі.

## 6. Аналіз результатів
**Чи правильно агент обирав tools?**
Так, у всіх функціональних кейсах набір tools збігся з очікуваним, зайвих викликів не було.
* TC-003 «Порадь веганський салат до 250 грн і скажи, чи він доступний»: `search_items` (параметри `category=salads`, `dietary_tags=[vegan]`, `max_price=250`), потім `check_availability` для знайденого `DISH-004`.
* TC-004 «Хочу 2 чіа-пудинги і лимонад...»: два `search_items` в одному кроці (по одному на позицію), далі `check_availability` для обох id і `calculate_order` з кількостями 2 і 1. Результат 385 грн і 5 хв збігається з очікуваним.
* TC-002: модель сама розклала запит на параметри (`category=drinks`, `dietary_tags=[lactose_free]`, `max_price=100`).
Неточність: у TC-005 агент не перевірив наявність лосося (див. нижче).

**Де агент помилявся і чому?**
Помилки були знайдені під час розробки, кожна виправлена й перевірена повторним прогоном:

| Етап                         | Помилка                                                                               | Причина | Виправлення |
|------------------------------|---------------------------------------------------------------------------------------|---------|-------------|
| Перші запуски графа          | Складний запит відповідь без жодного tool з вигаданими цінами; `</think>` у відповіді | Немає системного промпту, увімкнене міркування | `SYSTEM_PROMPT` (заборона відповідати зі знань, порядок tools), `reasoning=False`, `temperature=0` |
| Перший прогін `test_runner`  | TC-001/002: «десертів немає»                                                          | Модель неправильно формувала параметри пошуку (найімовірніше, тип страви потрапляв у `query`) | Чіткі `description` полів `category`/`dietary_tags`, підказка в `message` відповіді tool |
| Перший–другий прогін         | TC-003, TC-004: у відповіді зникли доступність і час приготування                     | `formatter` переписував відповідь агента й стискав її | `answer` береться з повідомлення агента без змін |
| Перший–другий прогін         | TC-005: у замовленні лише борщ, лосось зник без пояснення                             | `search_items` приховує недоступні страви, агент не врахував сигнал | `unavailable_matches` + `note` у відповіді tool, правило в промпті, програмна гарантія в `formatter` |
| Перший–другий прогін         | TC-006: «5+5=10/15 хвилин»                                                            | Після зупинки formatter сам додавав час, а реальний час 5 хв | Підсумок після зупинки лише з результатів tools |
| Третій прогін                | TC-003: 111 с, `confidence 0.3`                                                       | Просили Qwen3 переписати довгий текст у JSON: модель зациклилась на `</think>`, видала невалідний JSON і `confidence = 1.0000000000000002` | Структурований вивід лише для `confidence` і `sources` (`num_predict = 200`), інструкція йде останнім повідомленням, значення обрізається до [0, 1], прапорець `formatter_fallback` |

Що лишилось у фінальному прогоні:
* **TC-005.** Агент знову не згадав лосось: `search_items` повернув `unavailable_matches`, але агент перевірив і порахував лише борщ. Користувач бачить попередження лише завдяки програмній гарантії у `formatter` («Увага: зараз недоступно: ...»). Тобто промпт сам не гарантує потрібну поведінку, а критичні факти надійніше перевіряти кодом.
* **TC-006** навмисно обмежений `max_steps = 2`: запобіжник спрацював, відповідь позначена `⚠️`, `confidence = 0.3`. Ціни не обчислювались (`calculate_order` не викликано), і підсумок їх не вигадує.
* **TC-007 і TC-008** запущені на заглушці LLM, тому текст відповіді не обов'язково відповідає запиту: у TC-007 заглушка передає `max_price`, і formatter описує напої замість десертів. У TC-008 бачимо слово «глютenu» зі змішаними алфавітами. Це дрібний збій генерації локальної моделі, на висновки про запобіжники він не впливає.

**Кроки: simple vs complex.**
Кількість кроків дорівнює 1 + кількість послідовних «раундів» tools. Simple: один раунд → 2 кроки (TC-001, 002). Medium: два раунди (search → check) → 3 кроки (TC-003). Complex: три раунди (search → check → calculate) → 4 кроки (TC-004, 005). Паралельні виклики в одному раунді (два `search_items` у TC-004/005) нових кроків не додають. Залежність лінійна від кількості потрібних раундів tools, а не від «складності» запиту як такої.

**Чи досягав агент max_steps або timeout?**
Реальні ліміти (15 кроків, 120 с) жодного разу не досягнуті: максимум 4 кроки і 5,9 с. Запобіжники спрацювали лише там, де це було навмисно: TC-006 (`max_steps = 2`), TC-007 (`timeout = 0.5 с` при затримці заглушки 1 с, зупинка на другому вході в `agent`), TC-008 (третій однаковий виклик поспіль, `loop_detected`). У всіх трьох випадках користувач отримав часткову відповідь із поясненням, а граф завершився без винятків.

**Залежність часу виконання від складності.**
Час залежить від кількості викликів LLM і довжини згенерованого тексту, а не безпосередньо від складності. За логами: рішення викликати tool займає ≈0,6–1,3 с, фінальна відповідь ≈0,9–3,8 с (залежно від довжини), `formatter` ≈0,6–1 с, виконання самих tools менше 10 мс. Тому simple TC-001 (5,9 с, довга відповідь з тегами й алергенами) повільніший за medium TC-003 (3,1 с, коротка відповідь). Найдовший complex TC-004 (5,9 с) складається з чотирьох викликів LLM.

**Випадки, коли агент НЕ використав tool, хоч мав би.**
* TC-005: агент не викликав `check_availability` для лосося, бо `search_items` приховав його серед `unavailable_matches`, і позицію було відкинуто без перевірки. Недоступність виявлена лише за підказкою tool.
* На початку розробки (до посилення системного промпту, у `test_results.json` не потрапило): на складний запит про замовлення агент відповів без жодного tool і вигадав ціни. Після `SYSTEM_PROMPT` усі функціональні кейси використовують потрібні tools.
* У TC-006 частину tools не викликано через `max_steps = 2`, це очікувана поведінка.

## 7. Висновки та обмеження
- **Що працює добре:** агент правильно вибирає й комбінує tools (search → check → calculate), коректно витягує параметри з природної мови, Pydantic-валідація повертає зрозумілі помилки, запобіжники зупиняють виконання без збоїв, траєкторія повністю відтворює кожен крок.
- **Що можна покращити:** додати timeout на сам виклик LLM і `formatter`; оцінювати `confidence` не самою моделлю, а за результатами tools; додати автоматичний повтор виклику для недоступних позицій (пропозиція заміни); покращити морфологічний пошук українською (зараз обрізання закінчень); перевірити більшу модель.
- **Відомі обмеження:**
 - Timeout перевіряється лише між кроками агента: уже запущений виклик Ollama він не перериває.
 - `confidence` оцінює сама модель, значення не калібровані.
 - Часткові відповіді після зупинки формуються LLM і не проходять додаткової перевірки.
 - Автоматичний статус тестів евристичний (tools + ключові слова), TC-007/008 виконано на заглушці LLM.
 - Локальна модель недетермінована: окремі прогони можуть відрізнятися, іноді трапляються збої генерації (змішані алфавіти).
 - Дані меню статичні (`mock_data.json`), немає реальної інтеграції з API.
